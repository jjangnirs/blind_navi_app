# Safe Cross KR 개발 문서 묶음

> 작업명: Safe Cross KR  
> 목적: 대한민국 시각장애인·저시력자의 보행과 횡단보도 접근을 돕는 Android 우선 내비게이션 앱  
> 문서 기준일: 2026-09-04  
> 상태: 발견·설계 단계(Draft 0.2 — 횡단보도·신호 융합 반영)

## 1. 이 문서 묶음이 하는 일

이 폴더는 신입 개발자가 AI 코딩 도구와 함께 프로젝트를 시작할 수 있도록 제품 요구사항, 소프트웨어 요구사항, 기술 설계, 데이터 출처, 구현 순서와 복사해 쓸 수 있는 프롬프트를 한데 모은다.

중요한 전제는 다음과 같다.

- 공공데이터의 신호등·횡단보도 정보는 주로 **위치와 시설 속성**이다. 현재 적색·녹색 상태를 전국 단위로 실시간 제공하는 데이터가 아니다.
- 한국도로교통공단·지자체가 별도로 제공하는 실시간 신호정보는 정적 공공데이터와 다른 동적 데이터다. 공식 협약·사용승인을 받은 지역에서만 선택적으로 연계한다.
- `음향신호기 있음`인 곳에서는 앱이 시설의 위치와 접근을 알린다. 실제 횡단 판단은 현장 신호, 보행 환경, 사용자 판단을 함께 사용한다.
- `음향신호기 없음`인 곳의 카메라 AI는 횡단보도 형태와 방향, 보행자 신호, 두 객체의 연결 관계를 **함께 추정**한다. 한 프레임의 결과만으로 “건너세요”라고 명령하지 않는다.
- 공식 실시간 신호, 카메라 신호, 횡단보도 방향, GPS·방위 중 하나라도 충돌하면 점수를 평균내지 않고 `UNKNOWN`으로 처리한다.
- 알 수 없거나 충돌하는 경우 결과는 항상 `UNKNOWN(판단 불가)`이며, 앱은 정지·재확인을 안내한다.
- 이 앱은 흰지팡이, 안내견, 보행훈련, 물리적 음향신호기 또는 사람의 도움을 대체하지 않는다.

## 3. 권장 MVP 범위

전국 서비스를 곧바로 출시하지 않는다. 광주 생활권의 현장 검증된 횡단보도 20~30개를 선택하여 제한 베타로 시작한다.

MVP에 포함한다.

1. SK TMAP 공식 전국 POI 통합검색 및 기기 Geocoder 2차 폴백 (전국 모든 역, 관공서, 상호, 도로명 주소 실시간 위경도 검색, 내 위치 거리 계산 및 5km 보행 초과 뱃지 안내)
2. TMAP 보행자 경로 API를 통한 기본 보행 경로 (보행로 facilityType 11 표준 교정을 통한 육교 오안내 버그 완전 제거)
3. 대한민국 국토교통부 VWorld 표준 2D 정밀 전자지도 엔진 (전국 1:1000 골목길, 건물명, 횡단보도 100% 한글 표출 및 OSM/CartoDB 3중 자동 폴백)
4. 보행 안내 화면(NavigationScreen) 실시간 세부 지도 카드 및 내 위치 펄스 마커(🔵) / 경로 이탈(🔴) 시각 피드백
5. 경로 주변 횡단보도·신호등·음향신호기 위치 안내
6. 경로 분기점(회전/횡단) 즉시 음성 안내(`QUEUE_FLUSH`) 및 30m/15m 사전 접근 알림
7. 저시력자를 위한 전용 초고대비 대형 방향 안내 표시기(84dp 심볼, 38sp 대형 거리, 4dp 노란 테두리)
8. 시각장애인 특화 음성 길안내 포맷터(1~12시 시계 방향, 보폭 0.65m 기준 걸음 수 환산, TMAP 시각 단서 필터링, 신체 회전각 안내)
9. 지자기 회전 센서(ROTATION_VECTOR) 기반 실시간 나침반 헤딩 추적 및 햅틱 콤파스(경로 방향 정대 시 톡톡 2회 진동 및 상태 카드)
10. 횡단보도 접근 시 카메라 보행 보조 자동 연동(TriggerCrossingAssist)
11. GPS 정확도와 데이터 최신성 표시
12. 온디바이스 카메라 기반 2단계 하이브리드 보행신호 추정 파이프라인 (`TwoTierHybridSignalEstimator`):
    - Tier 1: LiteRT 딥러닝 객체 검출 모델(`LiteRtPedestrianSignalEstimator`)의 보행신호등 바운딩 박스 선검출 (미검출 시 배경 초록색과 무관하게 즉시 `UNKNOWN` 강등 차단으로 Zero False-Green 보장)
    - Tier 2: 신호등 박스 한정 적응형 HSV 정밀 분석 (`CameraVisionSignalEstimator.estimateWithinRoi`, 한국 경찰청 에메랄드/청록색 Green 및 고채도 Red 규격 파장 검출, 다크 하우징 콘트라스트 검증으로 간판/전광판 오탐 배제, 한낮 상단 적색 렌즈 햇빛 반사광(Phantom Light) 및 원거리 이격 신호등 필터링)
    - Tier 3: 온디바이스 기하·동역학·시간 일관성 검증기 (`LocalVlmSignalVerifier`, IoU 공간 추적기 및 점프 시 버퍼 리셋, 이동 차량 $v > 0.85/\text{sec}$ 기각 모션 필터와 동일 기둥 수직 램프 전환 분리, 5프레임 롤링 윈도우)
    - 핸드헬드 보정: 조준선(Reticle) 3프레임 유예 디바운싱 및 `GREEN_ESTIMATE` 1.8초 음성 발화 보호
13. 횡단보도 영역·진행 방향 인식과 목표 보행신호 연결
14. 여러 프레임·위치·방향·장면 문맥을 함께 확인하는 안전 상태기계
15. 승인 지역의 공식 실시간 신호정보를 위한 선택적 어댑터와 충돌 차단
16. TalkBack, 큰 터치 영역, 고대비, TTS, 진동 패턴
17. 네트워크가 끊겼을 때 캐시된 경로·시설 및 온디바이스 AI 사용 (FastAPI 백엔드 프록시 및 외부 HTTPS 터널 지원)
18. 잘못된 시설 정보 신고와 운영자 검수 흐름
19. 최근 검색 목적지 및 즐겨찾기(⭐) 영구 저장소 (`RecentDestinationRepository`, SharedPreferences JSON 기반 영구 저장, 앱 재시작 후 지속성 보장, 즐겨찾기 우선 4단계 동적 추천 큐)
20. 멀티밴드 GNSS 및 야외 정밀 위치 수신 최적화 (`ProductionLocationSource`, Android 12+ Fused Location 연동, Galaxy S25 Ultra 등 L1+L5 듀얼 주파수 지원, 부팅 시계-절대 시계 불일치 자동 폴백)
21. 횡단보도 정지/감속 구간 방위각 요동 내성 완화 필터 (`CrossingApproachEngine`, 18m 근접 또는 보행 속도 1.2m/s 이하 시 110도 허용으로 연석 접근 시 횡단보도 Drop 원천 방지)
22. 온디바이스 비전 지각 비행기록장치 (`PerceptionFlightRecorder`, 300프레임 무잠금 원형 링 버퍼 기반 텔레메트리 로깅, 카메라 영상/좌표 유출 없는 제로-프라이버시 아키텍처, 이상 징후 자동/수동 진단 덤프)

MVP에서 제외한다.

- 차량 접근·속도 판단
- “안전하니 건너라”는 보증 또는 자동 횡단 명령
- 카메라 영상의 서버 전송·상시 저장
- 승인·연계되지 않은 전국 모든 교차로의 실시간 신호 상태
- 계단·공사·불법주차 등 모든 보행 장애물의 완전 탐지
- 보호자 실시간 위치 공유(별도 법률·동의 설계 후 검토)

## 4. 신입 개발자의 시작 절차

### 4.1 개발 전 사람과 현장을 먼저 준비한다

1. 시각장애인 당사자 5명 이상, 보행훈련 전문가 1명 이상, 접근성 QA 담당자 1명을 자문그룹으로 구성한다.
2. 지자체·경찰서 교통시설 담당자와 공공데이터의 최신성·관리번호 의미를 확인한다.
3. 한국도로교통공단과 광주 교통 담당기관에 보행자용 실시간 신호정보의 제공 범위·계약·신선도·방향 코드 문서를 요청한다.
4. 광주 내 후보 횡단보도 20~30개를 선정한다.
5. 두 명이 한 조가 되어 시작점·끝점, 진행 방위, 횡단보도 polygon, 연결된 보행신호 ID, 음향신호기, 점자블록, 턱낮춤, 촬영 가능 위치를 현장 점검한다.
6. 카메라 AI는 처음부터 실제 사용자에게 안내하지 않고 `shadow mode`로 결과만 기록한다. 카메라 단독과 횡단보도·지도·시간축 융합 결과를 별도로 비교하며, 원본 영상 저장은 별도 동의를 받은 연구기기에서만 한다.

이 여섯 단계가 끝나기 전에는 일반 사용자를 대상으로 횡단 안내 베타를 시작하지 않는다.

### 4.2 Windows 11 개발 도구 설치

아래 도구는 각 공식 사이트의 최신 안정판을 사용한다.

1. Git for Windows
2. Android Studio(내장 JDK 사용)
3. Docker Desktop + WSL 2
4. Python 3.12 이상
5. VS Code(선택)

PowerShell에서 설치 확인:

```powershell
git --version
python --version
docker --version
docker compose version
```

Android Studio에서 새 프로젝트를 만들 때:

- Template: Empty Activity
- Language: Kotlin
- UI: Jetpack Compose
- Minimum SDK: API 28(Android 9)
- Package 예시: `kr.safecross.mobile`

`targetSdk`와 `compileSdk`는 구현 시점의 최신 안정 Android SDK로 설정하고, 의존성은 version catalog(`libs.versions.toml`)에 고정한다.

### 4.3 권장 저장소 구조

```text
safe-cross-kr/
├─ android-app/             Kotlin, Compose, CameraX, LiteRT
├─ backend/                 FastAPI API
├─ data-pipeline/           공공데이터 수집·정규화·검증

├─ infra/                   Docker Compose, 배포 설정
├─ docs/                    이 문서 묶음
├─ .github/workflows/       CI (backend, data, android, secret-scan)
├─ .env.example             키 이름만 포함, 실제 키 금지
├─ Makefile                 반복 명령 (Linux / macOS / WSL)

```

### 4.4 로컬 개발 및 테스트 실행 방법

#### Windows PowerShell 환경
```powershell
# 1. 가상환경 생성 및 의존성 설치
.\run.ps1 bootstrap

# 2. 코드 스타일 린트 검사
.\run.ps1 lint

# 3. 단위 테스트 실행 (backend 및 data-pipeline)
.\run.ps1 test

# 4. PostGIS 데이터베이스 컨테이너 구동/중지
.\run.ps1 backend-up
.\run.ps1 backend-down

# 5. 시크릿 및 금지 안전 문구 스캔
.\run.ps1 secret-scan

# 6. Android 빌드 및 단위 테스트 (JDK/Android SDK 필요)
cd android-app
.\gradlew.bat test
.\gradlew.bat assembleDebug
```

#### Bash (Linux / macOS / WSL) 환경
```bash

# 2. 코드 스타일 린트 검사

# 3. 단위 테스트 실행 (backend 및 data-pipeline)
make test

# 4. PostGIS 데이터베이스 컨테이너 구동/중지
```

### 4.5 프로젝트 생성 순서

1. 이 폴더의 문서를 새 저장소 `docs/`에 복사한다.
2. `SKILL.md`를 저장소 루트에 둔다.
3. `VIBE_CODING_PROMPTS.md`의 0번 마스터 프롬프트를 AI 코딩 도구의 프로젝트 지침으로 지정한다.
4. 1번부터 한 번에 하나의 프롬프트만 실행한다.
5. 각 단계에서 AI가 실행한 테스트 결과를 직접 확인한다.
6. 실패한 테스트를 삭제하거나 완화하지 말고 원인을 수정한다.
7. 안전 관련 변경은 최소 2명의 리뷰를 받고, 접근성·ML·현장 검증 체크를 모두 통과한 뒤 병합한다.

## 5. 팀 역할 최소 구성

| 역할 | 최소 인원 | 책임 |
|---|---:|---|
| 제품책임자 | 1 | 범위·우선순위·기관 협의 |
| Android 개발자 | 2 | 위치·카메라·접근성·오프라인 기능 |
| 백엔드/데이터 개발자 | 1~2 | API·PostGIS·ETL·운영 도구 |
| ML 엔지니어 | 1~2 | 데이터셋·모델·온디바이스 최적화 |
| QA/접근성 담당 | 1 | TalkBack·현장·회귀 시험 |
| 시각장애인 자문단 | 5+ | 요구 검증·사용성·현장 베타 |
| 안전/법률 자문 | 필요 시 | 위치정보·개인정보·서비스 문구 검토 |

한 사람이 여러 역할을 맡을 수 있지만, 개발자가 자기 안전 기능을 단독 승인해서는 안 된다.

## 6. Definition of Done

기능이 “완료”되려면 다음을 모두 만족해야 한다.

- 관련 요구사항 ID와 테스트 ID가 연결되어 있다.
- 단위·통합·접근성 테스트가 통과한다.
- TalkBack을 켜고 화면을 보지 않은 채 핵심 흐름을 완료할 수 있다.
- 네트워크, GPS, 카메라, 모델 중 하나가 실패해도 `UNKNOWN`으로 안전하게 축소된다.
- 횡단보도와 보행신호의 연결을 고유하게 확정하지 못하거나 공식 신호와 카메라가 충돌하면 `UNKNOWN`이다.
- 로그에 좌표 원문, 목적지, 카메라 프레임, API 키가 남지 않는다.
- 안전 문구는 “추정”을 분명히 말하며 “건너세요”를 사용하지 않는다.
- 실제 기기에서 지연시간, 발열, 배터리 소비를 측정했다.
- 변경 전후 모델·데이터·앱 버전을 재현할 수 있다.

## 7. 바로 다음 행동

1. `DATA_SOURCES.md`의 공공데이터포털 링크에서 전국 신호등·횡단보도 CSV를 내려받는다.
2. 광주 관련 행만 추출하되 현재 행정구역 명칭과 과거 명칭을 모두 검색한다.
3. 결측률과 좌표 범위를 검사한다.
4. 현장 후보 20~30개를 지도에 표시한다.
5. 각 진행 방향별 횡단보도↔보행신호 연결표를 만든다.
6. 공식 실시간 보행신호정보를 받을 수 있는 교차로와 받을 수 없는 교차로를 구분한다.
7. 당사자 자문그룹과 함께 위험이 낮고 반복 시험이 가능한 5개 교차로를 1차 모델 평가 장소로 확정한다.
8. 그 다음 `VIBE_CODING_PROMPTS.md`의 프롬프트 1을 실행한다.
